# 小红书数据采集系统 — 问题记录与解决方案

> 文档版本：v1.0 | 更新日期：2026-02-13

---

## 一、登录与会话相关

### 问题 1：服务器无图形界面，无法扫码登录

**背景**：小红书网页版登录需要手机扫描二维码，但服务器是纯命令行 Linux 环境，没有显示器和桌面环境，无法直接展示二维码。

**尝试方案**：
- 方案 A：截取二维码图片通过 API 转发到本地浏览器显示 — 可行但无法处理后续的滑块验证和短信验证
- 方案 B：刷新截图文件 — 延迟高，无法交互操作

**最终方案**：WebSocket 远程浏览器

在服务器上启动 Playwright 无头浏览器打开小红书登录页，每 300ms 截取一帧 JPEG 画面通过 WebSocket 推送到用户浏览器，用 Canvas 实时渲染。用户的鼠标点击、键盘输入通过 WebSocket 回传给服务器，由 Playwright 在无头浏览器中执行。相当于一个只转发浏览器窗口的简化版远程桌面。

**技术细节**：
- 画面：JPEG quality=40，分辨率 1024x680，帧率约 3 FPS
- 输入：每帧最多处理 20 个积压事件，事件轮询超时 5ms
- 登录检测：通过浏览器内 JS fetch 调用小红书 `/api/sns/web/v1/user/selfinfo` 接口验证
- Cookie 持久化：登录成功后自动提取 `web_session` 等 Cookie 保存到 `data/cookies/xhs_cookies.json`

### 问题 2：扫码后前端状态不更新，误报"登录成功"

**现象**：打开登录页面，还没扫码就显示"登录成功"。原因是浏览器数据目录中残留了旧的 Cookie，系统错误地判断为已登录。

**根因**：初始的登录检测逻辑只检查页面 UI 元素（如二维码弹窗是否消失），不校验 Cookie 是否真的有效。旧 Cookie 过期但仍存在，UI 上看不到登录弹窗，就误判为已登录。

**解决方案**：

引入双重验证机制：
1. **初始检查**（页面加载时）：不信任 UI 元素，直接通过浏览器内 JS 执行 `fetch('https://edith.xiaohongshu.com/api/sns/web/v1/user/selfinfo')` 调用小红书用户信息 API，根据返回的 HTTP 状态码和数据判断 Cookie 是否真的有效
2. **轮询检查**（扫码等待中）：监测 `web_session` Cookie 值是否发生变化 + 二维码弹窗是否消失 + API 验证三重确认

---

### 问题 3：二维码每秒刷新，无法正常扫码

**现象**：登录页面上二维码图片每秒更换一张，用户来不及扫码。

**根因**：前端轮询 `/api/login/qrcode` 接口的间隔设置为 1000ms，每次轮询都会触发后端重新截图，导致二维码图片不断刷新。

**解决方案**：
- 前端轮询间隔从 1000ms 调整为 3000ms
- 后端增加二维码有效期跟踪（小红书二维码有效期为 1 分钟）
- 新增 `_auto_refresh_qrcode()` 函数：在二维码过期时自动点击刷新按钮或重新加载页面
- 过期关键词检测更精确化：使用 `"二维码已过期"`、`"二维码已失效"`、`"重新获取二维码"` 等特定文案，避免误匹配

---

### 问题 4：远程浏览器无法输入短信验证码

**现象**：小红书触发短信验证，用户需要输入验证码，但通过远程浏览器的键盘事件转发无法正常输入文字到输入框中。

**根因**：Playwright 的 `keyboard.press()` 只能逐个发送按键事件，对于带有前端输入框监听和校验的场景（如验证码输入框），单纯的按键事件无法正确触发输入框的值更新。

**解决方案**：
- 在前端新增独立的文本输入框和"发送"按钮
- 用户在本地输入框中输入完整验证码后点击"发送"
- 后端收到 `type` 事件后调用 Playwright 的 `page.keyboard.type(text)` 方法一次性输入完整文本
- 同时新增"退格"和"清空"按钮，分别对应 `Backspace` 和 `Ctrl+A → Backspace` 操作

---

### 问题 5：远程浏览器连接后一直显示"等待浏览器启动"

**现象**：前端 WebSocket 连接成功后，始终停留在"已连接，等待浏览器启动..."状态，后端日志持续报"截图失败"。

**根因**：WebSocket 处理使用了 `async with _ws_lock` 全局锁，当一个客户端断开但锁未释放时，新客户端被阻塞。同时截图发送函数没有检查连接状态，在客户端已断开后仍尝试发送数据。

**解决方案**：
- 去除全局锁，改用 `_ws_active` 变量标记当前活跃连接
- 新连接到来时自动关闭旧连接（踢出机制）
- 新增 `_ws_safe_send_json()` 和 `_ws_safe_send_bytes()` 安全发送函数，发送前检查连接状态
- 客户端断开后立即终止发送循环

---

### 问题 6：Session 过期导致爬虫运行中断

**背景**：小红书的 `web_session` Cookie 会定期过期（约 24 小时），爬虫如果连续运行超过这个时间，API 请求会因为 Cookie 过期而全部失败。

**解决方案**：开发 Session 保活脚本 (`tools/session_keeper.py`)

- 每 3 小时用 Playwright 打开小红书页面，触发 Cookie 自动刷新
- 刷新后将最新的 Cookie 保存到共享文件
- 爬虫运行时自动跳过保活（通过 SingletonLock 检测）
- 爬虫启动时优先读取共享 Cookie 文件，确保使用最新凭证

## 二、爬虫运行相关

### 问题 7：`TypeError: list indices must be integers or slices, not str`

**现象**：爬虫在 `mark_completed()` 或 `mark_failed()` 时崩溃，错误信息指向 `self._failed.pop(url, None)` 或 `self._failed[url] = error`。

**根因**：`BatchProgress` 类的 `_failed` 字段期望是 `dict`（`{url: error_msg}`），但进度 JSON 文件中的 `"failed"` 字段在某些情况下变成了 `list`（`[]`），可能是手动编辑文件或旧版本代码写入造成的。`list` 类型的 `.pop()` 只接受整数索引参数，不接受字符串 key。

**解决方案**：

三层防御：
1. **加载时兼容**（`_load` 方法）：检测 `failed` 字段类型，如果是 `list` 则自动转为空 `dict`
2. **写入前检查**（`save` 方法）：每次保存前调用 `_ensure_failed_is_dict()` 确保类型正确
3. **操作前检查**（`mark_completed` / `mark_failed` 方法）：每次操作前先调用类型检查函数

```python
def _ensure_failed_is_dict(self):
    """防御性检查：确保 _failed 始终是 dict"""
    if not isinstance(self._failed, dict):
        self._failed = {}
```

同时手动修复了进度文件中的 `"failed": []` 为 `"failed": {}`。

### 问题 8：日期过滤不生效，每批 30 条才判断一次

**现象**：设置了日期范围 2025-01-01 至今，但爬虫在翻到 2024 年的旧帖后仍然继续爬取大量无效数据。日志显示连续多条"作品日期早于 2025-01-01"但不停止。

**根因**：系统架构分为两层：
- 外层 `get_all_notes_by_creator()`：负责分页，每页从 API 拉取 30 条笔记列表
- 内层 `_fetch_all_notes_detail()`：逐条获取详情，在这里检查日期

内层的 `early_stopped` 标志只在当前批次（30 条）内生效，无法传递回外层分页循环。即使当前批次判断应该停止，外层仍会继续拉取下一页 30 条。

**解决方案**：批次级别的日期停止机制

```
第1批(30条): 有超期笔记 → batch_old_count = 1
第2批(30条): 有超期笔记 → batch_old_count = 2 → 触发停止
第3批: 不会执行
```

实现：
1. 在 `_fetch_all_notes_detail()` 中跟踪本批次是否包含超期笔记
2. 批次结束时设置实例变量 `self._consecutive_old_batches` 和 `self._early_stop_requested`
3. 外层 `get_all_notes_by_creator()` 在每次 callback 后检查 `_early_stop_requested` 标志
4. 连续 2 个批次有超期笔记 → 停止翻页（容忍 1 个批次的置顶帖干扰）
5. 中间出现全新数据的批次 → 计数器重置为 0

### 问题 9：爬虫崩溃后数据已保存但未标记完成，导致重复爬取

**现象**：第 2 个作者（Spark Math线上课程）爬取了 2873 条数据并保存到 JSON 文件，但在调用 `mark_completed()` 时因 `_failed` 类型错误崩溃。重启爬虫后，该作者不在"已完成"列表中，于是从头重新爬取。

**根因**：`mark_completed()` 在 `self._failed.pop(url, None)` 处崩溃（问题 7），进度文件没有更新。

**解决方案**：
1. 修复了 `_failed` 的类型安全问题（问题 7 的解决方案）
2. 对比验证新旧数据：新爬的 124 条与旧的 2873 条完全不重复（0 条重叠），数据互补
3. 手动将该作者的完整 URL 添加到进度文件的 `completed` 列表中
4. 后续合并新旧数据即可

**验证过程**：
```
旧数据: 2873 条 (2869 唯一 note_id)
新数据: 124 条 (124 唯一 note_id)
重叠:   0 条
结论:   新数据全部是旧数据没有的内容，无需去重
```

### 问题 10：远程浏览器延迟大，验证码 1 分钟失效来不及操作

**现象**：短信验证码有效期 1 分钟，但远程浏览器画面延迟较高，从收到验证码到输入完成经常超时。

**根因**：
- 帧间隔 500ms（2 FPS），画面不够流畅
- 每帧只处理 1 个用户事件，输入响应慢
- JPEG 质量 60，图片体积大传输慢
- 浏览器窗口 1280x800，截图面积大

**解决方案**：五项优化
1. **帧间隔 500ms → 300ms**：帧率从 2 FPS 提升到约 3 FPS
2. **每帧处理事件 1 → 20**：一次处理所有积压事件，输入响应显著提升
3. **事件等待超时 20ms → 5ms**：更快进入截图环节
4. **JPEG 质量 60 → 40**：图片体积减小约 30%，传输更快
5. **窗口 1280x800 → 1024x680**：截图面积减小约 32%

## 三、数据质量相关

### 问题 11：爬取的数据包含日期范围外的笔记

**现象**：设置了 2025-01-01 之后的日期范围，但数据中包含少量 2024 年甚至 2023 年的笔记。

**根因**：小红书 API 返回的笔记列表是按时间倒序排列的，但夹杂了置顶帖和推荐内容。在翻页过程中到达日期边界前，已经获取了一些夹杂在中间的旧帖。

**处理方式**：
- 爬取阶段：通过批次级别的日期停止机制，2 个连续批次有超期笔记时停止
- 聚合阶段：在 `collect_crawled_data()` 中按日期范围严格过滤，移除超出范围的记录
- 旧帖数量极少（约占 3%），不影响整体数据质量

---

### 问题 12：部分笔记互动数据为空字符串

**现象**：某些笔记的 `liked_count`、`collected_count` 等字段为空字符串 `""`。

**根因**：小红书 API 对于互动量很低（如 0 赞）的笔记不返回具体数值，字段值为空。

**处理方式**：
- 在数据聚合和导出阶段，空字符串视为 0
- 互动量过滤时：`int(liked_count or 0) + int(collected_count or 0) + int(comment_count or 0)`

## 四、部署运维相关

### 问题 13：SSH 断开后爬虫进程终止

**现象**：通过 SSH 启动爬虫后，关闭终端或网络断开，爬虫进程也随之终止。

**根因**：SSH 终端关闭时会发送 SIGHUP 信号给所有子进程，导致进程退出。

**解决方案**：使用 tmux 终端复用器

```bash
# 在 tmux 中启动爬虫
tmux new-session -d -s crawler 'conda run -n uvenv python -m tools.batch_crawler'

# SSH 重连后查看
tmux attach -t crawler

# 在 tmux 会话内部切换
tmux switch-client -t crawler

# 启用鼠标滚动查看历史
tmux set -g mouse on
```

tmux 在服务器后台持续运行，不受 SSH 连接状态影响。

---

### 问题 14：多个 tmux 会话嵌套无法 attach

**现象**：执行 `tmux attach -t crawler` 报错 `sessions should be nested with care, unset $TMUX to force`。

**根因**：当前终端已经在一个 tmux 会话内部，tmux 默认不允许嵌套。

**解决方案**：使用 `tmux switch-client` 切换而非 attach

```bash
tmux switch-client -t crawler    # 切换到 crawler 会话
tmux switch-client -t 3          # 切换到 session 3
```

---

### 问题 15：爬虫日志只写文件不输出到控制台

**现象**：启动爬虫后终端没有任何输出，只有日志文件在更新。

**根因**：日志配置只添加了 `TimedRotatingFileHandler`，没有添加 `StreamHandler`。

**解决方案**：
- 在日志配置中同时添加文件 Handler 和控制台 Handler
- 启动命令加 `PYTHONUNBUFFERED=1` 和 `-u` 参数禁用 Python 输出缓冲
- 使用 `conda run --no-capture-output` 避免 conda 截获输出

```bash
PYTHONUNBUFFERED=1 conda run --no-capture-output -n uvenv python -u -m tools.batch_crawler
```

---

### 问题 16：日志文件无限增长

**现象**：长时间运行后日志文件占用大量磁盘空间。

**解决方案**：配置 `TimedRotatingFileHandler` 按天轮转

```python
handler = TimedRotatingFileHandler(
    filename="logs/crawler.log",
    when="midnight",        # 每天午夜轮转
    interval=1,
    backupCount=14,         # 保留 14 天
    encoding="utf-8"
)
```

## 六、经验总结

1. **防御性编程**：对外部数据（JSON 文件、API 返回）永远不信任类型，加载时做类型检查和转换
2. **断点续爬是必须的**：长时间爬取任务随时可能因网络、风控、Bug 中断，必须有可靠的进度持久化
3. **反爬不是一次性配置**：需要根据实际被风控的频率动态调整参数，对数正态分布比均匀分布更像真人
4. **远程操作需要容错**：WebSocket 连接随时可能断开，所有发送操作都需要 try-catch 和连接状态检查
5. **日志是调试的生命线**：同时输出到文件和控制台，保留足够天数，关键操作都要有日志
6. **分层架构便于排查**：调度层、爬虫层、API 客户端层、存储层各司其职，Bug 容易定位到具体层级
